DATA INTEGRITY REVIEW (revenue monorepo). Read-only review, no files changed. Line numbers are from the files as read. Items marked "unverified" were not traced end to end.

SUMMARY: The revenue write path is the strongest part. RevenueRecord has private setters, a validating constructor, a Version concurrency token, a unique (Org, Vehicle, Date) index, and replay-idempotent saves. The weak spots are the generic entities (User, Role, etc.), the missing concurrency-exception mapping on the revenue endpoint (unverified), float/locale handling in the shared formatters, and thin edge-case tests.

== 1. DOMAIN INTEGRITY ==

[HIGH] apps/api/Domain/Entities.cs:6-48 and Domain/Access.cs:3-49. User, VerificationCode, TrustedDevice, RefreshToken, Role, PersonRole, PersonPermissionOverride and AuditEvent are anemic bags of public setters.
- Risk: anything can set User.Status, FailedAttempts, PausedUntil, PinHash, Revoked or Consumed directly. Lockout and consume rules (the "Tell, Don't Ask" invariants) live outside the entity, so any caller can bypass them. Email and PhoneNumber are plain strings, so an unnormalized phone can be persisted.
- Fix: add methods (RegisterFailedAttempt(now, threshold), Pause, Consume(now), Revoke, SetPin) with private setters. Make PhoneNumber/Email value objects.
- Related: Access.cs:48 `OccuredAt` is misspelled. AuditEvent is mutable, so audit rows can be edited. Make it init-only or private set.

[MEDIUM] Domain/Entities.cs:15 User.SecurityVersion and VerificationCode/RefreshToken have no concurrency token.
- Risk: parallel PIN-attempt increments lose updates (FailedAttempts races, so brute-force lockout can be bypassed). Parallel refresh-token rotation allows double use of one token.
- Fix: add a rowversion or IsConcurrencyToken on User and RefreshToken, or use an atomic `UPDATE ... SET FailedAttempts = FailedAttempts + 1`.

[MEDIUM] Domain/Organization.cs:78-86, 120-122, 142-160. Organization.Slug/Name and OrganizationMembership.FirstName/LastName/ApprovalLimit use public setters. OrganizationLocalization is entirely public setters (lines 146-156), with validation at line 162 only when something calls it.
- Risk: invalid locale, NumberDecimals or ApprovalLimit (negative) can be set without validation. OrganizationMembership.Version has a public setter (line 122), so the optimistic-lock counter can be forged or reset. Organization.SettingsVersion is only bumped if callers remember SettingsChanged() (line 86), which is an easy-to-forget manual step.
- Fix: private setters on Version, and bump it in the mutating methods or in SaveChanges.

[LOW] Domain/PhoneNumber.cs:5-39. It is a static normalizer returning "" for invalid input, not a value object.
- Risk: "" is a silent sentinel, so an invalid number can flow into User.PhoneNumber. Tabs and spaces are mixed on lines 7-39. It duplicates the normalization in packages/shared/src/format.ts:99-106, which has different semantics: it never rejects, it returns "0..." local form where the API returns "+254...", and it accepts a 254-prefixed number of any length. The `/^[17]/` branch prefixes "0" to anything starting 1 or 7, regardless of length.
- Fix: make it a `readonly record struct PhoneNumber` with `TryParse`/`Create` that throws, and have the web and mobile shared code mirror the same rules. Add shared test vectors.

[OK] Domain/Revenue.cs:54-120 RevenueRecord. Private setters, a validating constructor, UTC enforcement, business date immutable, Version++ in Replace, CorrectedAfterDate set in the entity, and a tenant guard on OrganizationId. Infrastructure/RevenueModel.cs:14-17 has precision (14,2), a concurrency token on Version, and a unique index.
- [LOW] Revenue.cs:80 `businessDate == default` is accepted only at the constructor. Replace trusts the caller's `today` and `updatedAt`, so CorrectedAfterDate depends on the caller passing the right value.
- [LOW] Revenue.cs:21/66-72 Money() (Domain/Setup/PsvCompany.cs:66) caps at 999,999,999,999.99 and requires <= 2 decimals. The client regex `\d{1,12}(\.\d{1,2})?` matches, so client and server agree. Good. But NumberDecimals (0-6) is a display setting only and is not coupled to storage precision. See the format finding below.

== 2. REVENUE DATA FLOW ==

[HIGH, unverified] apps/api/Application/RevenueUseCases.cs:71 and :86-99. The version check `input.Version != existing.Version` is a read-then-write check. Two concurrent PUTs that both read version N both pass it. EF's concurrency token on Version should then throw DbUpdateConcurrencyException on the second SaveChanges, and for first captures the unique index throws DbUpdateException. I found no mapping of these exceptions in the revenue endpoint. Grep shows 409 mapping only in SetupEndpoints.cs:33-34 (settings) and OrganizationRepository.cs:82. If it is not mapped, concurrent saves return 500 instead of 409+current. The mobile queue's `status >= 500` falls to `return false`, so the capture is retried until it hits the proper 409. That is safe, but the web shows a generic error.
- Fix: catch DbUpdateConcurrencyException/DbUpdateException in the revenue save path and rethrow RevenueConflictException with a re-read record. Add a test for two concurrent saves.

[MEDIUM] packages/shared/src/revenue.ts:15-22 parseRevenueAmount. It returns `Number(text)`, a JS double. Up to 12 integer digits plus 2 decimals is 14 significant digits, which is within the double range of 15-17 digits, so the value round-trips today. But the JSON number then goes into C# `decimal`, and sums on the client use doubles. `Number("0.1")` + `Number("0.2")` style drift would appear if the client ever sums amounts (see difference() below). The comma/space stripping `[,\s]` also accepts "1,2,3" as "123" and "1 2" as "12". A mistyped "1,25" (decimal comma) silently becomes 125, a 100x revenue overstatement.
- Fix: reject malformed thousands grouping (`^\d{1,3}(,\d{3})*(\.\d{1,2})?$|^\d+(\.\d{1,2})?$`). Consider carrying amounts as strings or integer minor units.
- Also: the schema stores "no earnings" as null amount + reason, but REVENUE_AMOUNT_ERROR says "positive", so a legitimate KES 0 day cannot be recorded without picking a reason. Product decision, not a bug. Note that the server's Money() also rejects 0.

[MEDIUM] packages/shared/src/revenue.ts:30-40,84-89 RevenueCell/SaveRevenue. `version?: number | null` is optional, so a client can omit it. The server treats null Version on an existing record as a conflict, which is correct, but the TS type permits forgetting it. `reason` is `string | null` on RevenueCell but `RevenueReason | null` on SaveRevenue, so the type is loose on read. `status` plus `amount`/`reason` can be inconsistent (for example status "amount" with amount null) because the types are not a discriminated union. Make RevenueCell a discriminated union on status.

[MEDIUM] apps/web/components/RevenuePage.tsx:578. `share = cell.expected ? Math.round((actual / cell.expected) * 100) : 0` correctly guards divide-by-zero, but returns 0% (shown red, since < 90) when expected is 0, rather than "n/a". Server-side `percent` is `number | null` and the page handles null at lines 265, 358, 392, so this one cell path is inconsistent.
- Also line 589: `Math.min(share, 100)` is fine.

[LOW] apps/web/components/RevenuePage.tsx:638. `const [opened] = useState(cell)` intentionally snapshots the version, so a correction sends the version it was opened at (comment at lines 636-637). This is correct design (an unseen newer record yields a 409). But if the 409 conflict branch uses `conflict.current.version` (line 738) for "Replace with mine", the user overwrites after seeing the current value, which is right.
- Lines 689-693: after a 409 with no body.current, `reload()` is awaited with `.catch(() => undefined)`. If the reload fails, the user sees only the generic message, with no retry affordance. Fine.
- Double-submit is guarded with a `busy` ref (lines 666-676). OK.

[MEDIUM] apps/web/components/revenueFormat.ts:32-33. `figure()` is `kes(value).slice(currencyCode().length + 1)`. This is string surgery on formatted output. With a locale where the currency is positioned after the number, or with RTL or non-breaking spaces from toLocaleString, it slices the wrong characters. kes() hard-codes "CODE number" ordering today, so it works, but any change to kes() breaks figure() silently.
- Fix: expose `formatNumber(amount)` in shared/format.ts and build kes() from it.
- Line 36-41 difference(): `Math.round((actual - expected) * 100) / 100` is fine for 2-decimals. It does hard-code 100, ignoring NumberDecimals (see below). `-0` is handled because `gap === 0` is true for -0.

[LOW] packages/shared/src/dates.ts:67 `calendarDate(value)` has no validation. An invalid string gives an Invalid Date, and `shiftDate` then throws a RangeError at `toISOString()`. `isDate` only checks the shape, so "2026-02-31" passes isDate, and `new Date("2026-02-31T00:00:00Z")` is Invalid Date in V8. Mobile queue.ts:92 `isDate(entry.date)` therefore admits impossible dates into the queue, which the API rejects with 400 and the queue marks `failed`. That is recoverable (the user can discard), but not ideal.
- Fix: make isDate round-trip check (`calendarDate(v).toISOString().slice(0,10) === v`).
- Line 100-121 dateParts: `hour: "2-digit"` with `hourCycle: "h23"` is fine. Some engines return "24" for midnight with hour12:false, but hourCycle h23 avoids that. OK.
- Line 163-175 formatTimestamp: a bad `value` yields an Invalid Date and `Intl` throws a RangeError, so a malformed timestamp crashes the render. Guard with `isNaN(date.getTime())`.
- Timezone model: business dates are treated as UTC calendar days throughout (good, with no local-clock use). The server's actor.Today comes from the org time zone. The web and mobile only use `businessDate` from the API. No timezone bug found in date arithmetic.
- startOfWeek: `(weekdayIndex - weekStartsOn + 7) % 7` is correct. `daysBetween` uses Math.round of ms / DAY, which is DST-safe because it is UTC.
- apps/mobile/src/revenue/dates.ts:43 weekHolding: `Math.ceil(daysBetween(date, currentWeekStart)/7)` is correct for dates on or before the current week. For a date after currentWeekStart it yields a negative or zero shift (`Math.ceil(-0.3)` = -0, giving -7*-0 = 0 or +). Future dates are rejected by the API anyway.

[HIGH, offline queue] apps/mobile/src/revenue/queue.ts. The design is careful (slot plus index write ordering, per-owner mutex, replay idempotency). Findings:
1. queue.ts:362-401 `add()` for an existing key overwrites the slot with a NEW entry whose `version` is whatever the caller passes. If a capture is `conflict`/`blocked`, and the user re-captures that day, the earlier conflict information (`current`) is dropped, which is fine. But if a send of the OLD entry is in flight (`send(entry)` already awaiting apiPutResult), the old PUT may succeed on the server. The result then calls `update(entry, "remove")`, whose guard `now.entry !== sent` is true, so the removal is skipped. The new entry stays and is re-sent with the old `version` (null, for a first capture). Server: existing record now exists, so version null !== N gives 409 and the user's newer value is shown as a conflict against their own earlier value. No data is lost, but the user sees a spurious "Someone else saved this day first." Fix: on 409, if `problem.current` equals the entry's own amount/reason/note, treat as success, or, when an entry is replaced mid-flight, carry the accepted version forward (use the RevenueSaved.Version from the 200 response to rebase the replacement's `version`).
2. queue.ts:288-290 / 294-303: on a 409 whose `problem.current` matches the queued value (an identical replay of a different version), the server's Matches() check short-circuits before the version check (RevenueUseCases.cs:50), so this is already handled server-side. Good.
3. queue.ts:290 `status >= 200 && < 300` deletes the capture. Correct. But the 200 body's Version is discarded. See 1.
4. queue.ts:378 `queuedAt: Date.now()` is used for ordering during recovery (line 208). A device clock moved backwards could make an older capture win over a newer one when duplicates exist after a crash. Use a monotonic counter persisted in the index.
5. queue.ts:119-128 `exclusive` swallows errors for chaining via `next.catch(() => undefined)` but returns `next`, so callers still see them. OK.
6. queue.ts:345 `if (closed || !(await send(entry))) return;` aborts the whole round on the first transient failure. This preserves ordering (earlier day first). A single poison entry that returns 5xx forever blocks all later entries. 400/403/404 are moved to failed, so only 5xx or network can block. Acceptable, but consider a retry cap for repeated 5xx.
7. queue.ts:72-85 validSaved: `typeof saved === "object"` is true for null. If `saved` is null, then `saved.amount` throws TypeError. `orNull(entry.current, validSaved)` guards null before the call, so it is safe in this path. But `validSaved` is not safe if reused.
8. queue.ts:93 `REVENUE_REASONS.includes(entry.reason!)` is fine. validCapture does not check that `note` is null when reason is not "Other" or that "Other" has a note, so a hand-corrupted slot could be sent, but the API validates.
9. QueueFull: 500 limit, bit string. Fine.

== 3. STATE MANAGEMENT ==

[MEDIUM] apps/web/lib/data/useResource.ts:15-24. On reload (version bump with the same path), the old data stays visible while refetching, with no `loading` flag. `loading` is `path !== null && !current`, so a background reload is invisible. Stale data is shown with no indicator during a refresh, and after a save it reads as fresh. The error branch keeps the old data and sets `error`, so the user sees both stale data and an error (fine). There is no request de-duplication or cache, so there is no cache invalidation problem, just per-hook state: two components that fetch the same path can diverge after a save (for example the dashboard cards vs the revenue grid) because nothing signals the other hook to reload. Fix: expose `refreshing`, and add a lightweight invalidation bus (or SWR/TanStack Query with keys).
- No AbortController. `active` flag ignores stale responses, so the data is correct, but the in-flight request is still made.
- Line 19-23: when the path changes and fails, `data` is undefined (correct, no cross-path leakage).

[MEDIUM] apps/web/lib/data/useStreamedList.ts:30-66. (a) `progressive` is computed from `shown.current !== path`, so a reload on the same path swaps in only when complete (good). (b) Pagination race: pages are fetched sequentially by offset while the underlying list can change (a row inserted or deleted between pages), which gives duplicate or skipped rows. There is no de-dupe by id, and no cursor. For an audit/change log this is a real inconsistency. Fix: keyset or cursor pagination, or de-dupe by id and verify `total` at the end. (c) The `done` test `items.length >= total || result.items.length === 0` is okay. (d) On error mid-stream, `setLoaded(current => ({...current, path, done: true, error}))`. If `current.path` is a previous path, stale items from the previous path are carried under the new path (the spread keeps `items`), so a failed first page of a new path shows the old path's rows. Fix: `items: current.path === path ? current.items : []`.

[LOW] apps/web/lib/session-context.tsx. It is a bare context with a default of `can: () => false`, so no stale-state bug here. But permissions are loaded once, and the server re-checks every write (confirmed in Save: WriteAny + permission checks). If an admin changes someone's access, the web session's `can` stays stale until reload (UI-only drift; the server stays authoritative). Consider revalidating on 403.

[MEDIUM] apps/mobile/src/session.ts:15-29. `fetchPerson` persists the person (permissions, role) to local storage. Offline, the app uses the cached permissions after the server may have revoked them (the access.ts comment says "The server remains the authority", which is true for writes). The queue then holds entries the API rejects with 403, which become `failed`. That is correct behavior, but the UI offered the capture. Also, `kept.userId ? ... : kept.phoneNumber === phoneNumber` falls back to a phone match for legacy records (a phone can be reassigned, as the queue.ts comment itself acknowledges). Low risk.
- Line 17-27: a `person` object is constructed without a type annotation, then saved (`StoredPerson`). If `session.permissions` is undefined (API change), `allowedTabs` (access.ts:67) would throw on `.includes`. Validate it.

[LOW] apps/mobile/src/shell/access.ts:145-160 periodLabel. `weekStartsOn = firstDayOfWeek()` is evaluated at call time from module-global `formats` (shared/format.ts:33, a mutable module singleton). `configureFormats` is global, so on web SSR (Next.js) concurrent requests would share one `formats`. Verify configureFormats is never called on the server per request. The same applies to every shared formatter (`kes`, `formatDate`), as they read the global. On the client this is fine. Risk: cross-user leakage of locale on the server render, and re-render staleness since components do not subscribe to format changes (a change in the org locale does not re-render memoized components).

== 4. DATA TRANSFORMATION ==

[HIGH] packages/shared/src/format.ts:49-58 kes(). `maximumFractionDigits: formats.numberDecimals` rounds the display. The server stores 2 decimals. With NumberDecimals = 0 (allowed 0-6, Organization.cs:162), 1,500.50 displays as "1,501" (or "1,500" with half-even), so the displayed figure and the stored/summed figure disagree. Rows will not visibly sum to the totals. With NumberDecimals > 2 it pretends to precision the data does not have. Also, `Number.isInteger(amount) ? 0 : decimals` means KES 1,500 and KES 1,500.50 have different widths in a column (alignment only). Fix: clamp numberDecimals to 0-2 to match storage precision (server-side validation at Organization.cs:162 should be `is < 0 or > 2`), and always format with the same fraction digits in tables.
- `amount.toLocaleString` with `NaN`/`undefined` renders "NaN" (no guard). Null amounts must be filtered by callers. `kes(null)` throws at the type level only.
- `Math.abs` of -0 and `money()` (line 60-62): `amount < 0` fine. Float rounding of the sum happens before the call. `kes(-amount)` for -0.004 would show "KES 0 loss" (a negative that rounds to zero is labeled a loss). Fix: round first, then test sign.
- Formats typo `useGroupping` (double p) leaks to the API contract (Organization.cs:152 `UseGroupping`). Renaming needs a migration, so note it but low priority.

[MEDIUM] packages/shared/src/format.ts:68-70 percentText. `${percent}%`: no rounding or NaN/Infinity guard. If the caller passes a fractional percent it shows "83.33333333%". The server returns the percent, so confirm it is an integer (the web test says "shows as it is"). Negative percent is not handled. Fix: `Math.round`.

[MEDIUM] DRY/duplication.
1. Phone normalization is implemented twice with different semantics (C# Domain/PhoneNumber.cs vs shared format.ts:99-135), plus the API-side Regex duplicates in AuthService/UserProvisioning (unverified). Add cross-language golden vectors.
2. Date label formatting is split across `packages/shared/src/dates.ts` (mediumDateLabel, compactDateRange), `apps/mobile/src/revenue/dates.ts` (dayLabel, rangeLabel, longDayLabel, shortDayLabel, which duplicate web revenueFormat.ts `shortDate/longDate/weekday`, but the mobile version ignores the org datePattern: it hard-codes the "medium" format via mediumDateLabel, whereas the web uses `formatDate` which honors the pattern/locale). So a "short" or "long" date pattern setting changes the web but not the phone. This is a user-visible inconsistency. Fix: have the mobile use shared `formatDateOnly`.
3. Both apps have `rangeLabel`. Web uses `formatDateRange`, which respects the pattern and falls back to "from to through". The mobile uses compactDateRange directly (always compact).
4. `compactDateRange` line 188 does `formatDate(from).replace(/ \d+$/, "")`, which assumes the format ends with a trailing day-number. That is true for the "{day} {mon} {year}" medium label only if year is last. Here the label is "28 Sep 2026", and this regex strips " 2026" (a trailing number, which is the YEAR), giving "28 Sep to 4 Oct 2026". It works by accident of the year being the trailing number (the comment suggests the intent). Fragile if the medium pattern changes.
5. Duplicate "percent" logic: server `percent`, web RevenuePage.tsx:578 `share`, and weekly totals. Compute once on the server (already) and render only.
6. `monthlyEstimate` (apps/web/components/recurringPresentation.ts:87-97): `Math.round(amount * 30.4)`/`4.35`: approximations (365/12=30.42, 52/12=4.333), so weekly 4.35 overstates by 0.4%, and daily 30.4 is slightly low. It rounds to whole shillings (loses cents), and it is an "estimate" per the comment, but if it feeds totals (net contribution) it is a financial inaccuracy. Use 52/12 and 365/12 for exactness, and use the same function as the server (check for a server-side equivalent, unverified).
7. recurringPresentation.ts:33-63 recurringNextPostings: (a) `onDay = candidate.getUTCDate() === (item.lastDay ? lastDay : item.day)`. For monthly `day` = 31 in a 30-day month, or 29/30/31 in February, it never matches, so that month is skipped entirely (no posting). The UI and the server may differ on this (server rule unverified). Fix: clamp day to the month's lastDay (the standard "monthly on the 31st means the last day of shorter months" behavior), and make the server identical. (b) The scan is capped at 3660 days (about 10 years), which is fine for yearly with 5 postings (needs 5 years). (c) Weekly with `item.day` null never matches (silent). (d) `item.start > today` string comparison is valid for ISO dates.
8. `ordinal(value)` in dates.ts:58: `["th","st","nd","rd"][value % 10] || "th"` is correct for 1-31.
