OPERABILITY REVIEW (revenue monorepo). I read Program.cs, appsettings.json, the shared auth client, both web proxy routes, body.ts, request.ts, both data hooks, the mobile api.ts and queue.ts, and the file inventory. I only skimmed Api/*.cs (via grep of catch/Log/Problem), the repositories, UseCases and Security.cs, so line numbers outside the files I read in full are approximate. Revenue-change audit trail: I found a change-log migration, a "change log" feature and a retry on change-log collisions in OrganizationRepository.cs:70, but I did not verify that every revenue write records the actor.

CRITICAL
1. Deployment: there is no CI/CD and no container or deploy artifact. The repo has no Dockerfile, no docker-compose, no .github/workflows and no GitLab pipeline. The only .gitlab content is duo/agent-config.yml. Nothing builds, tests or lints on a PR, and there is no migration or release process. Recommendation: add a pipeline (npm ci, lint, typecheck, test:web/test:shared, mobile jest, dotnet build/test) and Dockerfiles for the API and the web app.
2. Deployment: the API runs EF migrations and the user-provisioning CLI inside web startup. Program.cs:114-158 runs `MigrateAsync()` on every instance start, and the migration-history rename SQL at :122-127 runs on every start. With more than one replica, concurrent migrations race. A slow or failed migration also blocks startup and the platform restart loop hides the cause. `--provision-user` and `--remove-user` share the same boot path. Recommendation: run migrations as a separate step (a migration bundle or an init job) and move the CLI commands out of the web host.

HIGH
3. Logging: logging is the default console provider with no structured sink, no request logging, no correlation or trace ID and no metrics. Program.cs has no Serilog/OpenTelemetry, no UseSerilogRequestLogging and no ProblemDetails `traceId` customization. appsettings.json:20-22 sets only Default=Information. Recommendation: add OpenTelemetry (traces, metrics, logs) or Serilog JSON with a request ID, and put the trace ID in ProblemDetails.
4. Error handling: `app.UseExceptionHandler()` (Program.cs:101) is used with no handler, and Logging has no `Microsoft.AspNetCore.Diagnostics` override. Unhandled exceptions get a generic ProblemDetails, which is good. Application code, though, logs almost nothing: grep found only Security.cs (mailer), Program.cs and the ChangeLog retry. Endpoints SetupEndpoints.cs:30-34 map UnauthorizedAccess, KeyNotFound, ArgumentException, DbUpdateConcurrency and DbUpdateException to 4xx without logging. A DbUpdateException turned into 409 loses the real cause (FK, truncation, deadlock or timeout all look like a "conflicting record"). SetupEndpoints.cs:30 and :32 also return `error.Message` as detail for ArgumentException and UnauthorizedAccessException, which risks leaking internals if a lower layer throws one with a technical message. Recommendation: log at Warning or Error with the exception for the DbUpdateException branch, and only surface messages from a dedicated validation exception type.
5. Observability and health: `/health` (Program.cs:110) is a static `{status:"ok"}` that does not touch the database, and it is unauthenticated. There is no `AddHealthChecks()`, no readiness probe, no DbContext check and no liveness/readiness split. A dead DB still reports healthy, so the load balancer keeps routing to a broken instance. Recommendation: use AddHealthChecks().AddDbContextCheck<AuthDb>() with separate /health/live and /health/ready, plus a health check on the web app (none exists).
6. Configuration: the SQL connection string defaults to Integrated Security (appsettings.json:3) and there is no appsettings.Production.json. Email creds, SigningKey and the connection string must come from env or secrets, and nothing documents or validates this. Startup throws if SigningKey is under 32 bytes, which is good. In production nothing validates the Email:Host/From/Username/Password options, so SmtpEmailSender fails only on the first send. Recommendation: validate options at startup (ValidateOnStart), add production config, use a secret store.
7. Resilience (mobile): there is no timeout on any fetch. `reach()` (mobile api.ts:39-45) calls `fetch` with no AbortSignal and no timeout. A hung connection stalls the offline queue's `send()`, because `running` stays set and `sync()` never completes. The `syncing` spinner is also stuck. Recommendation: wrap fetch in `AbortSignal.timeout(15-30s)` and treat the abort as OfflineError.
8. Resilience (queue): the queue has no backoff, no retry cap and no scheduling. In queue.ts:271-324 a 5xx or network failure returns false and stops the round. The next attempt only happens on app open, a new capture, a manual retry, or a network-state event (:473-476). So if the API is up but returning 500, the entry waits indefinitely with no exponential backoff, no jitter and no retry timer. There is also no visible "failed N times" state: 5xx and 429 map to `return false` with no recorded error. A permanently failing 5xx entry blocks every later entry, because the loop returns at the first failure (:345). Recommendation: record attempt count and lastError per entry, add timed backoff (and honour Retry-After), and skip or park a poison entry instead of blocking the whole round.
9. Error handling (queue): swallowed errors with no telemetry. sync() catch at queue.ts:348-350 swallows Keychain read/write failures silently, with nothing told to the user. `savedNow()` (:265) swallows all errors and returns null, so a failed fetch results in a conflict record with `current: null`. There is no crash/error reporting (Sentry or similar) anywhere in the mobile app. Recommendation: add reporting and surface "storage problem, entries may not be syncing".

MEDIUM
10. Error boundaries: there are no React error boundaries in web or mobile. grep for ErrorBoundary/componentDidCatch finds nothing in apps. apps/web/app has no error.tsx, global-error.tsx, loading.tsx or not-found.tsx (it contains only api/, globals.css, layout.tsx and page.tsx). A render exception gives a white screen on mobile and the default Next error page on web. Recommendation: add error.tsx and global-error.tsx on web and a root ErrorBoundary in mobile App.tsx.
11. Resilience (web hooks): `useResource` and `useStreamedList` have no retry, no timeout and no abort. useResource.ts:15 and useStreamedList.ts:77 never cancel the in-flight request (the `active` flag only ignores the result), so rapid path changes leave requests in flight. A transient 503 shows an error until the user clicks reload. In useStreamedList, a failure on page N keeps the first N-1 pages but marks `done: true` (:90-97) and sets an error, so partially loaded data can look complete. Its loop trusts `result.total` and breaks only when items.length >= total or a page is empty, so a changing dataset or a server returning a constant non-empty page could loop. Recommendation: add an AbortController, a bounded retry with backoff for GET (503/network), and a "partial result" flag.
12. Resilience (web proxy): the 15s timeouts are good, but timeouts and connection errors are not distinguished or logged. Every catch block (auth route.ts:47, :211; setup route.ts:381) is a bare `catch {}` that returns 503 and logs nothing. The auth POST path returns `{status:"authentication_failed"}` with 503, while the GET path and the setup proxy return "service_unavailable". The shared client keys its message off httpStatus (503) so the UI is fine, but the inconsistent body is a trap. Also, the 15s timeout can fire after the upstream committed a write, and there is no idempotency or `x-request-id`. Recommendation: log (with a request ID), unify the body, forward a correlation header to the API.
13. Resilience (mobile auth refresh): `renew()` (api.ts:93-109) has a single refresh attempt. If the refresh hits a network error it is rethrown (OfflineError), which is fine. A 401 after refresh throws SessionEndedError, which ends the session. A transient 5xx during refresh (AuthError with 503 is converted into SessionEndedError at :103) force-logs-out the user. Recommendation: only convert 401/400-class AuthErrors, not 429/5xx.
14. Error handling: `apiGet` (mobile api.ts:126-137) discards the server error body on 5xx and loses the trace ID, and `apiGet` throws plain `Error` with no status, so callers cannot distinguish 403/404/429. The web client has a typed ApiError but mobile does not. Recommendation: share one ApiError in packages/shared.
15. Config: hardcoded values that should be configurable. Rate limit window of 1 minute (Program.cs:62) is fixed, the fallback permit limit of 30 is hardcoded (:56), `AuthPermitLimit` is not in appsettings.json, and `UseRateLimiter` only covers the "auth" policy (apply it to the API at large). Other fixed values: the 10s mailer drain (:98), the 15s proxy timeouts, the 500 queue limit, the 72h offline window, and the 365/90-day cookie lifetimes. The API URL has localhost fallbacks (web: `process.env.API_URL || "http://localhost:5000"` in three places; mobile api.ts:19-23). In production a missing API_URL silently points at localhost. Recommendation: fail fast in production when API_URL or EXPO_PUBLIC_API_URL is unset, and move limits into options.
16. Config/security: `AllowedHosts: "*"` (appsettings.json:24), and CORS is built from config with `AllowAnyHeader().AllowAnyMethod()`. The CORS default is localhost only and there is no production override. Recommendation: set real AllowedHosts per environment.
17. Resilience (DB): `AddDbContext(UseSqlServer(...))` has no `EnableRetryOnFailure()` and no command timeout configuration, so transient Azure SQL/SQL Server faults surface as 500s. JWT `OnTokenValidated` (Program.cs:80-90) does two DB queries on every authenticated request (user + trusted device), which is an availability coupling and load concern. A DB failure there yields 401 or 500 semantics that clients (mobile `renew()`) read as an ended session. Recommendation: enable retry on failure, add caching or a short-lived check, and make sure DB errors give 503 rather than 401.
18. Deployment: the lock files are present (root package-lock.json and apps/api/packages.lock.json), which is good. But the root package.json has no `test:mobile`, no `typecheck`, no `build` for the whole monorepo and no API scripts (dotnet build/test/migrate). The apps/web `tsconfig.tsbuildinfo` is committed. The `engines` field requires node >=22.23.3, and there is no .nvmrc or global.json pinning the .NET SDK. `apps/api/bin/Debug` was seen in the tree (check it is gitignored; it did not show in `git ls-files`). Recommendation: add global.json, .nvmrc, an aggregate `ci` script, and remove the committed tsbuildinfo.
19. Deployment (mobile): there is no eas.json or build profile. app.json is the only config, and there is no environment separation (dev/staging/prod API URLs) beyond EXPO_PUBLIC_API_URL.
20. Logging/PII: the development email sender logs the verification code and the email address (Security.cs:98: "DEV EMAIL to {Email} ... code {Code}"). It is registered only in Development/Testing, so this is acceptable, but if ASPNETCORE_ENVIRONMENT is mis-set in staging the codes land in logs. Program.cs:138 logs the provisioned email, and Security.cs:139 logs user ids with correlation ids (good, since ids are not PII). The `developmentCode` field in AuthResponse and in the proxy output (auth route.ts:164) is forwarded to browsers whenever the API returns it. Recommendation: confirm the API never sets it outside Development, and add a guard that fails startup if LogEmailSender is used in a non-dev environment.
21. Observability: audit trail. Revenue and setup changes have a change log (migrations ChangeLogIsFilterable, OrganizationRepository.cs:70), which is a positive. But there is no audit of authentication events (sign-in failures, lockouts, device revocation, PIN reset) in logs, and no log of authorization denials (SetupEndpoints.cs:30 returns 403 silently). The change log is a DB table, not an immutable or exported record. Recommendation: log security events at Information/Warning with user id, device id and the client IP, and consider append-only protection for the change log.

LOW
22. Shared AuthError (packages/shared/src/auth.ts:86-103) is well designed: no internals leak, the message derives from status, and invalid JSON is mapped to authentication_failed (:122-124). The one weakness is that a non-JSON 5xx body from a gateway (HTML 502) becomes "authentication_failed" in the body, which is covered by the 503 branch only if the status is 503; a 502 or 504 gets the generic "Check your details" message, which blames the user. Recommendation: treat any 5xx as service_unavailable.
23. The auth proxy GET and POST both return `NextResponse.json({status:"invalid_request"}, {status:403/404})` with no `Cache-Control: no-store` on the early rejections (minor).
24. `readLimitedBody` is correctly bounded, and `forwardedFor` handles proxy hops safely. One gap: TRUSTED_PROXY_HOPS defaults to 0, so in a standard reverse-proxy deployment the API rate limiter sees one IP (the Next server) and the 30/min `auth` limit is shared by all web users unless this is configured. This needs documenting (README) and, ideally, a startup warning.
25. Graceful shutdown: it is handled for the mailer (Program.cs:98), but `.Wait(10s)` blocks synchronously in the stopping callback, and the default host shutdown timeout is 30s in .NET 10. The orchestrator termination grace period must exceed that. Also `app.Run()` is synchronous (:159).
26. `DotNetEnv.Env.NoClobber().TraversePath().Load()` (Program.cs:16) loads .env in every environment, including production, and walks up directories, which can pick up an unintended file. Consider restricting it to Development.

What is good (to preserve): request body limits, timeouts on web proxy fetches, path allowlists, a rate limiter keyed on forwarded client IP, a production guard on SigningKey, OpenAPI disabled in prod, an offline queue designed for crash-safety (per-slot writes, idempotent replay, conflict states), single-flight token refresh, lock files committed, ProblemDetails registered, HSTS in production builds.
