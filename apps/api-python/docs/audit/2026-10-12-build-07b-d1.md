## 2. Deviations from the documents, with reasons

All are written into `docs/07-auth.md` 12.16 and the `docs/05-routines.md` 10.1 rows.

- `api.auth_account_lookup` gained `p_pin_try`: a reset completion (A09, N06) must not record a
  PIN try for an unknown number, or a stranger's resets would move the simulated lock.
- The unknown-number code simulation exists only for `pin_reset`, keyed on `forgot_pin` rows (A07
  and N05 now record that operation): a purpose-blind simulation answered `triesLeft` where a real
  account with a PIN has no such code.
- `unknown_pin_tries` reads up to six rows, `unknown_code_tries`, `remove_devices` and
  `sign_in_snapshot` take `p_now`, `code_check` carries `tries_left`; `count_wrong_pin` and
  `api.auth_pin` dropped an unused device-name parameter.
- A reset completion whose checked hash changed answers `verdict_void` with nothing changed.
- Completions void a code on the third wrong try without a replacement (no replacement hash on
  that route).
- A03 refuses a pending forced reset; it checks no lock (a verified new device clears both).
- `needs_dummy_hash` covers a pending forced reset, not a missing membership (A01 keeps counting
  that account's wrong PINs).
- Device removals do not bump the user row's `version`.
- The A01 per-person one-code-a-minute rule (DN-B6-3) now holds a new-device code asked within a
  minute of any other code: the tests' `AuthApi.onboard` moves the clock 61 s after onboarding.
- Question 58 (brand host rules) did not go into `0008`: `0008` was applied to the development
  database before they could be written, and an applied migration is never edited. It moves to
  `0009_access` (D2); `docs/04` 13 and `docs/13` question 58 say so.
